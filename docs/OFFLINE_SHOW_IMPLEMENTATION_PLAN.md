## 01 먼저 결정할 방향

**추천 방향은 음원 사전 분석과 편집 가능한 조명 악보다.** 노래 전체를 분석해 초안을 만들고, 모의 전구로 확인한 뒤 어색한 부분을 고친다. 공연에서는 확정한 악보를 음악 재생 시각에 맞춰 실행한다. 분석기가 매 순간 즉흥적으로 전구를 켜는 구조는 주력에서 제외한다.

우리가 원하는 것은 파형을 그대로 빛으로 바꾸는 시각화가 아니다. 잔잔한 부분은 여백을 두고, 중요한 소리에는 한 쌍이 켜졌다 사라지며, 필요한 구간에서는 전체가 강하게 반응하는 연출이다. 어떤 소리를 강조할지는 분석 결과만으로 항상 정답을 정할 수 없다.

### 이번 계획의 핵심 약속

- 음악 분석 결과와 조명 악보를 별도 저장한다. 분석을 다시 해도 사람이 고친 악보를 자동으로 덮어쓰지 않는다.
- 분석기는 후보를 제공한다. 확실하지 않은 구간을 억지로 클라이맥스나 드럼이라고 이름 붙이지 않는다.
- 기능별 통과 기준을 먼저 정한다. 타격 수 감소나 단위 테스트 성공만으로 음악적으로 좋아졌다고 판단하지 않는다.
- 기존 Bridge 연결, 그룹 순서, 음원, 인증키를 보존한다. 이번 문서는 계획이며 기능 구현이나 데이터 이관은 하지 않았다.

### 첫 완성본의 사용 흐름

음원 선택 → 분석과 자동 초안 → 음악과 모의 전구 재생 → 어색한 지점 편집 → 저장과 확정 → 실제 전구 재생

| 첫 버전에 포함 | 첫 버전에서 제외 |
| --- | --- |
| 로컬 WAV와 MP3 사전 분석, 재생목록 | 유튜브 URL과 마이크의 완전 자동 공연 |
| 한 쌍 점등과 감쇠, 전체 펀치, 유지와 소등 | 자동 악기 분리와 정확한 화음명 인식 |
| 타격 추가·삭제·이동, 구간 효과 수정 | 모든 곡의 완벽한 클라이맥스 자동 판정 |
| A/B 배열, 기존 Hue Entertainment 출력 | 다중 Bridge 확장과 EXE 패키징 |

**승인 요청:** 이 제작 흐름과 단계별 검증 방식에 동의하면 0단계부터 착수한다. 분석 도구의 최종 채택은 비교 시험 후 결정한다. 앞부분만 읽을 경우 01, 07, 12, 13절을 먼저 보면 된다.

## 02 현재 프로그램에서 살릴 것과 바꿀 것

2026년 9월 16일 로컬 코드 기준으로 확인했다. 기능이 존재한다는 사실과 그 기능의 정확도가 검증됐다는 주장은 구분한다.

| 확인한 구성 | 현재 상태 | 이번 계획에서의 처리 |
| --- | --- | --- |
| Hue 장비 출력 | 연결, 영역 선택, 프레임 전송 구현 | 전송 어댑터 재사용 후 재검증 |
| 그룹과 배열 순서 | 같은 인덱스를 A/B 쌍으로 취급 | 논리 슬롯으로 보존 |
| 기존 음원 라이브러리 | 음원 파일과 analysis JSON 저장 | 기존 파일을 그대로 보존 |
| 기존 사전 분석 | app.js에 자체 분석 및 고정 간격 Beatgrid 경로 존재 | 외부 분석기와 새 시간축으로 대체 |
| 파형과 악보 편집 | 확대 파형, 구간·Cue 편집 일부 존재 | 화면 구성은 재사용 후보, 데이터 결합은 분리 |
| LedFx 실험 | 대역 분석을 자체 타격 규칙에 연결 | 비교용으로 유지, 새 악보와 동시 실행 금지 |

### 코드에서 발견한 구체적인 위험

**분석 선택과 저장이 결합돼 있다.** `upgradeSavedTrackAnalysis`는 저장된 곡을 선택하는 과정에서 분석을 갱신하고 서버에 저장할 수 있다. 새 경로에서는 선택만으로 쓰기가 발생하지 않도록 한다. 기존 데이터의 자동 변환 결과를 새 분석의 정답으로 취급하지 않는다.

**박자와 조명 타격의 이름이 혼재한다.** 기존 `beatTimes`는 실제 Beat 추적 결과와 동일한 뜻이 아니다. 새 형식에서는 `beats`, `onsetCandidates`, `lightingEvents`를 구분한다. 이름이 같다는 이유로 기존 배열을 새 필드에 복사하지 않는다.

**현재 서버의 예약은 공연용 큐 목록이 아니다.** `SendFrameAsync`는 0~250ms 예약과 `_pendingFrame` 한 개를 사용한다. 미래 프레임 여러 개를 계속 밀어 넣으면 앞선 예약을 대체할 수 있는 구조다. 새 재생기에서는 시간표 보관과 현재 프레임 출력을 분리하고 정지·탐색 때 예약을 무효화한다.

**기존 문서의 완료 표시는 구현 이력이다.** 이전 로드맵의 체크 표시를 음악적 품질 승인으로 이어받지 않는다. 새 계획의 단계별 평가 결과를 별도로 남긴다.

코드 근거: `wwwroot/app.js`의 `analyzeAudioBuffer`, `upgradeSavedTrackAnalysis`, `startAnalyzedPlayback`; `Program.cs`의 `/api/tracks`와 `SendFrameAsync`; `wwwroot/ledfx-show.js`. 모두 읽기만 했으며 이번 작업에서 프로그램 코드는 변경하지 않았다.

## 03 분석과 연출과 출력은 다른 문제다

**박자, 소리 시작, 조명 큐는 서로 다른 데이터다.** 이 셋을 구분해야 같은 실패를 반복하지 않는다.

| 용어 | 쉬운 뜻 | 조명에 바로 써도 되는가 |
| --- | --- | --- |
| Beat 박자 | 발로 일정하게 세는 음악의 맥박 | 모든 박마다 켤 필요는 없다 |
| Downbeat 마디 첫 박 | 하나 둘 셋 넷 중 첫 박 후보 | 강한 소리와 항상 같지 않다 |
| Onset 소리 시작 | 음이나 타격이 새로 시작된 후보 | 보컬과 장식음도 포함될 수 있다 |
| 에너지 | 소리 크기와 대역별 세기의 변화 | 새 타격의 증거 중 하나일 뿐이다 |
| 구간 경계 | 음악의 성격이나 반복이 바뀌는 후보 | 후렴이나 클라이맥스 확정이 아니다 |
| Cue 조명 큐 | 언제 어떤 전구를 어떻게 켤지 정한 명령 | 검토된 큐가 실제 출력의 기준이다 |

### 제안 구조

원본 음원 → 공통 재생용 음원 → 분석 작업자 → 분석 결과 보관

분석 결과 + 연출 규칙 → 자동 악보 초안 → 사용자 수정 → 확정 악보

확정 악보 + 음악 재생 시계 → 하나의 프레임 계산기 → 모의 전구 또는 Hue 출력

### 하나의 예로 보는 책임 분리

10초 부근에 분석 후보가 세 개 나왔다고 가정한다. 분석 결과에는 세 개를 모두 남길 수 있다. 연출 초안은 그중 강조할 후보를 고르고, 사용자는 불필요한 큐 두 개를 삭제할 수 있다. 삭제 때문에 분석 원본까지 바뀌지는 않는다.

확정한 큐가 음악의 10.2초라면 매번 같은 시각에 재생돼야 한다. 출력이 80ms 늦는다면 하드웨어 보정 문제다. 큐 자체가 10.0초에 잘못 찍혔다면 분석 또는 편집 문제다. 하드웨어 보정으로 잘못된 큐를 숨기지 않는다.

### 왜 이 방식인가

grandMA3는 타임코드에 이벤트를 기록하거나 직접 추가할 수 있고, xLights는 분석 타이밍과 배치한 효과를 분리한다. Eurovision 제작 사례도 사전 프로그래밍과 리허설 수정, 시스템 지연 보정을 구분한다. 여기서는 이 작업 흐름을 참고한다. 해당 제품을 구매하거나 그 코드를 그대로 가져온다는 뜻은 아니다. [S1][S2][S3]

## 04 분석 도구를 어떻게 고를 것인가

**추천 비교 조합은 librosa 기반 특징·소리 시작 분석과 Beat This 기반 박자 분석이다.** 서로 같은 일을 하는 도구가 아니므로 결과를 구분해서 사용한다. 지금 채택 확정이나 정확도 보장은 하지 않는다.

| 후보 | 맡길 역할 | 장점과 확인할 제한 | 제안 |
| --- | --- | --- | --- |
| librosa | 음량, 대역, onset 후보, 박자 비교 기준 | 기존 알고리즘을 재현하기 좋지만 onset이 드럼만 의미하지 않음 | 기준 분석 경로 |
| Beat This | Beat와 Downbeat 후보 | 학습된 추적기, CPU 실행 가능. Windows 설치·시간·오류 곡 확인 필요 | 우선 비교 후보 |
| madmom | 추가 박자 비교 | 코드와 모델의 라이선스가 다름. 모델 비상업 조건 확인 필요 | 초기 기본 배포에서 제외 |
| Essentia | 광범위한 특징과 모델 | 모델·라이브러리·의존성별 조건 검토 필요 | 초기 범위에서 보류 |
| LedFx | 실시간 반응 효과 비교 | 공연용 사전 악보 생성기와 목적이 다름 | 비교용으로만 보존 |

librosa의 onset은 스펙트럼 변화에서 후보를 찾으며 beat 추적은 별도 기능이다. Beat This의 기본 출력은 박자와 마디 첫 박자이지, 원하는 모든 ‘뚠’이나 조명 패턴이 아니다. [S4][S5][S6]

### 라이선스와 설치 검토

librosa는 ISC, Beat This는 코드와 공개 가중치를 MIT로 안내한다. 다만 배포하는 전체 패키지와 모델 출처, 음원 사용 권리는 별개로 확인해야 한다. madmom 모델은 비상업 조건이 명시돼 있고, Essentia는 공식 페이지 간 모델 조건 표기도 달라 개별 모델의 LICENSE 확인 전 채택하지 않는다. 법률 결론이 아니라 배포 전 확인 항목이다. [S6][S7][S8][S9][S10]

처음에는 새 Python 가상환경에서 CPU 기준으로 시험한다. 기존 LedFx 환경을 수정하지 않는다. 합격한 패키지·모델 버전과 해시를 고정하고 필요한 모델을 미리 준비해 현장에서는 인터넷이 없어도 동작하도록 한다. 모델 다운로드 실패 시 몰래 다른 분석기로 전환하지 않고 상태를 표시한다.

### 채택 기준

설치 성공만으로 채택하지 않는다. 동일한 곡 집합에서 타격·박자 정확도, 수정 필요량, CPU 분석 시간, 메모리, 무인터넷 실행, 라이선스를 비교한다. 고급 모델이 개선되지 않으면 추가하지 않는다. 드럼 분리와 화음명 인식은 원인과 이득을 확인하기 전에는 도입하지 않는다.

## 05 음원을 어떻게 분석할 것인가

### 1 파일과 시간 원점을 먼저 고정한다

원본 파일을 보존하고 파일 해시를 기록한다. WAV·MP3를 검사한 뒤 48kHz 스테레오 PCM WAV를 공통 재생 자산으로 생성하는 방안을 우선 시험한다. 분석과 재생은 같은 자산을 기준으로 한다. 앞부분 무음을 임의로 제거하거나 정규화한 소리로 교체하지 않는다. 파일 크기·길이 상한, 취소, 오류 상태를 제공한다.

분석기는 필요에 맞춰 리샘플링하되 모든 결과는 공통 음원의 0초로 되돌린다. 프레임 중앙 정렬, 모델 구간 겹침, 리샘플 지연을 메타데이터에 기록한다. 좌우를 단순 평균해 소리가 상쇄되는 파일도 검사한다. 분석용 분리 신호나 모노 신호가 재생 음원을 대체해서는 안 된다.

### 2 서로 다른 특징을 독립 추출한다

| 데이터 | 용도 | 저장 및 주의점 |
| --- | --- | --- |
| 파형과 RMS·Peak | 큰 소리, 작은 소리, 무음과 클리핑 확인 | 원래 단위와 상대 정규화 값을 함께 보존 |
| 저·중·고역 에너지 | 소리 분포와 강약 참고 | 저음이라고 킥으로 확정하지 않음 |
| Onset 강도와 시각 | 소리 시작 후보 | 전체 혼합음 기준, 타격 성분 분리 결과는 비교용 |
| Beat·Downbeat 시각 | 반복 리듬과 마디의 후보 | 고정 BPM으로 전곡 그리드를 재생성하지 않음 |
| 로컬 템포와 안정도 | 빠르기 변화와 불확실 구간 | 수치가 없으면 미확정으로 표시 |
| Chroma·변화량 | 화성적 변화와 구간 경계 보조 | 화음명이나 클라이맥스 정답으로 사용하지 않음 |

특징 간격은 약 10~20ms부터 시험하되 실제 sample rate와 hop 값을 저장한다. 10ms 간격으로 저장했다고 10ms 정확도가 보장되는 것은 아니다. 화면용 파형은 축약해도 사건 시각은 축약하지 않는다.

### 3 분석 품질을 검사한 뒤 저장한다

시각 배열의 정렬, 유한한 수치, 음원 범위, 중복 경계, 무음 구간, 샘플 수를 검증한다. 긴 곡을 조각낼 경우 겹친 부분의 동일 사건을 한 번만 남긴다. 분석기는 상대 점수만 제공할 수도 있으므로 이를 근거 없이 ‘정확도 95%’로 바꾸지 않는다.

구간 후보는 에너지·음색·반복 변화로 제안하되 처음에는 ‘조용함·리듬 강함·지속음 중심·미확정’ 정도로 표시한다. Intro·Chorus·Climax 명칭은 사용자가 확인할 수 있게 한다. 분석 작업이 끝나도 실제 전구는 켜지지 않는다.

## 06 데이터를 나눠 저장하고 수정본을 지킨다

**원본 분석, 자동 초안, 사용자 악보, 장비 설정을 분리한다.** 한 JSON을 계속 덮어쓰지 않는다. 아래 revision은 저장 버전, hash는 파일 내용이 같은지 확인하는 식별값을 뜻한다.

| 자료 | 핵심 필드 예시 | 변경 원칙 |
| --- | --- | --- |
| 음원 manifest | trackId, sourceHash, playbackHash, duration, sampleRate | 동일 이름이 아니라 해시로 동일 음원 확인 |
| analysis revision | analysisId, toolVersion, modelHash, parameters, beats, onsets, sections | 재분석은 새 revision 생성 |
| show revision | showId, analysisId, generatorVersion, events, sceneRanges, palette | 자동 초안과 사용자 저장본 별도 |
| 편집 이력 | eventId, add/move/delete, locked, baseRevision | 삭제 표시와 잠금, 되돌리기 보존 |
| 공연 장비 설정 | Bridge 식별자, slot mapping, timing profile | 곡의 음악 시각과 분리 |

### 조명 이벤트 한 개가 가져야 할 정보

예: `eventId=c12`, `timeSec=12.400`, `target=pair:2`, `effect=singlePulse`, `peak=0.70`, `attackMs=15`, `releaseMs=280`, `color=#FFB870`, `sourceEventId=o31`, `origin=manual`, `locked=true`.

숫자는 데이터 모양을 설명하는 가상 예시이며 현재 음원의 검출 결과가 아니다. 단위는 필드 이름으로 구분하고 내부에서는 동일 시간 단위를 사용한다. 연출 이벤트의 `peak`는 실제 광량이 아니라 제어 값이다.

### 재분석과 재생성은 덮어쓰기가 아니다

분석 A1에서 악보 S1을 만들고 사람이 S2로 고쳤다면, 새 분석 A2가 생겨도 S2는 그대로 남는다. A2 기반 초안을 새로 만들고 차이를 보여준 뒤 적용한다. 삭제한 큐는 자동 재생성으로 되살리지 않는다. 시간 근처라는 이유만으로 다른 사건을 동일 사건으로 병합하지 않는다.

첫 버전에서는 수동 편집본 전체를 잠그고 새 초안과 나란히 비교하는 보수적인 방법을 택한다. 정교한 변경 병합은 후속 기능으로 둔다. 구간 재생성은 명시적으로 선택한 미잠금 구간에만 적용한다.

### 파일과 장애 처리

새 자료는 `data/projects/<id>/` 아래로 격리하는 안을 권장한다. 임시 파일에 저장·검증 후 원자적 교체를 하고 이전 revision을 보존한다. 동시에 두 창에서 저장하면 revision 충돌을 알린다. 곡 목록 API에는 큰 특징 배열을 전부 싣지 않고 요약만 반환한다. 기존 analysis JSON의 크기 제한에 새 데이터를 억지로 끼워 넣지 않는다.

음원·분석·모델·인증키는 공개 Git에서 제외한다. 프로젝트 내보내기는 음원·악보·논리 배치가 대상이며 인증키와 가상환경은 제외한다. 새 PC에서 장비 설정을 다시 연결해도 곡의 편집 내용은 유지돼야 한다.

## 07 분석 데이터로 연출 초안을 만드는 규칙

**분석 후보를 모두 점등으로 바꾸지 않는다.** 먼저 구간의 연출 의도를 정하고, 그 구간에서 사용할 사건을 선택한다. 규칙과 선택 사유를 기록해 왜 켜졌는지 설명할 수 있어야 한다.

### 타격 선택

명확한 onset, 주변 대비 강도, 순간적인 타격 성분, 박자와의 관계를 각각 점수로 유지한다. 하나의 불투명한 점수만 저장하지 않는다. 박자 근처라는 이유만으로 선택하지 않고, 박자 밖의 의도된 당김음도 지우지 않는다. 낮은 점수는 검토 대상으로 남긴다.

아주 근접한 후보는 같은 소리인지 비교해 묶되, 일률적으로 0.8초 동안 금지하지 않는다. 30~80ms 범위의 중복 병합 같은 값은 비교 시험 대상이지 확정 음악 규칙이 아니다. 원하는 ‘강조할 소리’ 목록은 일반 onset 정답과 별도로 검토한다.

| 구간 프리셋 | 기본 연출 | 금지할 동작 |
| --- | --- | --- |
| 희소한 악센트 | 기본 소등. 선택한 악센트마다 다음 A/B 쌍 점등 후 감쇠 | 여운의 흔들림마다 재점등 |
| 리듬 중심 | 검토한 타격 또는 박 선택에 전체 펀치 | 모든 고역 장식음에 전구 이동 |
| 지속음 중심 | 낮은 밝기를 부드럽게 유지·변화, 또는 소등 유지 | 피크가 없다고 가짜 타격 생성 |
| 전환 강조 | 확인한 구간 시작에 색·패턴 변경 | 불확실한 경계에서 자동 암전·플래시 |

### 첫 패턴은 네 가지로 제한한다

`SINGLE_PULSE`는 한 쌍만 빠르게 켜고 완전히 감쇠한다. 다음 사건 때 이전 쌍은 0으로 만든다. `FULL_PULSE`는 모든 선택 전구의 밝기를 함께 올렸다 내린다. `HOLD`는 지정 상태를 유지한다. `OFF`는 명시적 소등이다. 파도·중앙 확장·무작위 색은 이 네 가지가 검증된 다음이다.

희소 패턴의 공격 10~30ms, 감쇠 200~400ms를 초기 디자인 범위로 시험한다. 다음 큐가 먼저 오면 이전 잔광을 종료한다. 강한 패턴은 타격 간격에 맞춰 감쇠를 제한하되 실제 장비가 구분하지 못하는 빠른 펀치는 경고하고 밀도를 낮춘다. 값은 목표 디자인이며 Hue의 보장 응답 속도가 아니다.

색은 기본 두세 색 팔레트를 구간별로 사용하고, 모든 타격에서 자동 순환시키지 않는다. 강한 구간의 음악적 설득력을 밝기 100%나 무조건 빠른 변화와 동일시하지 않는다.

같은 시각에 큐가 겹치면 비상 소등, 잠긴 수동 큐, 일반 수동 큐, 자동 큐 순으로 우선한다. RGB와 밝기를 무제한 더하지 않는다. 프레임마다 모든 대상의 상태를 명시해 이전 전구가 켜진 채 남지 않게 한다.

## 08 사용자는 무엇을 보고 무엇을 고치는가

### 기본 화면은 단순하게

재생목록, 분석 상태, 재생·정지, 모의 전구, 연출 편집 버튼만 기본으로 둔다. 실제 출력은 모의 출력과 명확히 구분하고 연결 준비를 마친 뒤 선택한다. 타격 민감도와 개발용 카운터를 공연 사용자가 매번 조절하게 하지 않는다.

‘선별된 소리 시작마다’ 같은 구현 용어의 체크박스는 없앤다. 한 쌍 프리셋을 고르면 다음 쌍 이동과 이전 쌍 소등이 패턴의 기본 동작이다. 개발 진단은 별도 접힌 화면에만 둔다.

### 편집 화면은 세 줄로 시작한다

1. 음악 줄: 파형, 박자 표시, 재생 위치. 전체 곡과 확대 구간을 함께 본다.
2. 분석 줄: 소리 시작 후보. 필요할 때만 펼치고 저음·고역 등의 참고 표시를 본다.
3. 연출 줄: 실제 켜질 큐와 구간 효과. 여기서 삭제·추가·이동하고 밝기·색·감쇠를 바꾼다.

클릭음은 박자, onset, 최종 조명 큐 중 하나만 선택해 듣는다. 여러 클릭을 동시에 울려 원인을 섞지 않는다. 사전 저장된 시각을 오디오 시계에 예약하고, 새 실시간 검출로 클릭을 생성하지 않는다. 재생 시각, 예정 큐 시각, 보정된 전송 시각은 개발 화면에서 구분한다.

### 수정 예시

| 들리는 상황 | 자동 초안이 잘못된 경우 | 사용자가 할 수정 |
| --- | --- | --- |
| ‘뚠’ 한 번 | 12.4초, 12.5초, 12.7초에 세 번 점등 | 남길 큐 하나 선택, 나머지 삭제 |
| 새 악센트가 있음 | 해당 순간이 비어 있음 | 재생 위치에 큐 추가 후 정확한 시각 조정 |
| 긴 소리만 이어짐 | 불필요하게 전구가 순환 | 그 구간을 유지 또는 소등 프리셋으로 변경 |
| 후렴 시작 | 여전히 한 쌍만 켜짐 | 구간 경계를 맞추고 전체 펀치로 변경 |

자동 박자 스냅은 기본 강제가 아니라 선택 기능이다. 보컬 진입이나 당김음은 박자선 밖에도 놓을 수 있다. 전체 큐를 이동하는 것과 장비 지연 보정은 다른 메뉴로 둔다. 실수는 실행 취소하고 마지막 확정본으로 되돌릴 수 있어야 한다.

확정 전 상태는 ‘초안’, 저장 후 검토한 버전은 ‘공연본’으로 구분한다. 공연 중에는 악보를 자동 재생성하지 않는다. 먼저 모의 출력에서 검토하고, 동일한 공연본을 실제 전구에서 실행한다.

## 09 음악과 전구 시간을 맞추는 설계

**분석 시각과 하드웨어 보정을 분리한다.** 음악 이벤트는 음원 시작 기준 초로 고정하고, 장소마다 달라지는 오디오·조명 지연은 장비 프로필에 둔다.

### 시계와 재생기

첫 웹 버전은 음악 재생 시계를 기준으로 진행한다. 브라우저 화면 갱신 횟수나 누적 `setInterval` 횟수로 음악 시간을 계산하지 않는다. 서버의 단조 시계와 브라우저 오디오 시계 사이 기준점을 잡고 주기적으로 오차를 확인한다. 왕복 지연의 절반을 항상 정확한 단방향 지연이라고 단정하지 않는다.

확정 악보의 계산기는 `현재 음악 시각 → 모든 슬롯의 상태`를 반환하는 결정적 함수로 만든다. 앞에서부터 재생했든 중간을 클릭했든 같은 시각이면 같은 상태여야 한다. 모의 전구와 Hue는 같은 논리 프레임을 사용하되 화면과 실제 전구의 물리 응답까지 같다고 주장하지 않는다.

서버에는 악보와 작은 재생 버퍼를 주고 현재 시각에 필요한 프레임을 계산하게 하는 방안을 우선 검증한다. 현재의 단일 예약 프레임 API를 긴 큐 목록처럼 재사용하지 않는다. 전송 주기는 우선 25~40ms 후보로 시험하며 장비 시험 후 고정한다. 늦게 쌓인 프레임을 연속 발사하지 않고 현재 상태로 따라간다.

### 보정 부호를 하나로 정의한다

내부 기준에서 소리가 귀에 도달하기까지 지연을 A, 명령 후 빛이 보이기까지 지연을 L이라고 하자. 음악 이벤트 시각 t의 명령 시각은 `t + A - L`이다. 같은 내부 시간 원점을 쓴다는 전제의 설명식이며 저장된 분석 시각을 변경하는 공식이 아니다.

예를 들어 A가 100ms, L이 150ms라면 전구 명령을 50ms 먼저 보내야 한다. 사용자에게는 ‘조명 앞당김 +50ms’로 표시한다. 조명이 먼저 보이면 이 값을 줄인다. 오디오 보정, 전구 보정, 예약 버퍼에서 같은 지연을 두 번 더하지 않는다. 버퍼는 미래 명령 전달을 위한 것이지 별도 음악 보정값이 아니다.

### 반드시 처리할 상태 변화

- 재생 준비: 장비 연결과 초기 소등 확인 후 카운트다운으로 음악·재생 기준점 시작.
- 일시 정지·탐색: 재생 세대 ID를 바꾸고 이전 예약 폐기. 새 시각에서 전체 상태 계산.
- 끝·정지·오류: 소등 프레임 전송과 연결 해제 시도. 실패하면 사용자에게 알림.
- 통신 두절·탭 비활성·PC 절전: heartbeat 만료 시 출력을 멈추고 가능한 소등을 시도. 끊긴 장비의 실제 소등은 보장할 수 없으므로 현장 수동 대책 필요.

웹에서 장시간 백그라운드 재생 기준을 통과하지 못하면 공연 모드는 전면 실행을 요구하고, 이후 EXE에서 오디오와 출력 시계를 한 프로세스로 합친다. EXE로 바꾼다고 검출 오류나 무선 지연이 저절로 해결되지는 않는다.

## 10 음악 분석과 연출의 위험 검토

아래는 예상 실패와 방어 방법이다. ‘발생하지 않음’이 아니라 ‘발생했을 때 구분하고 수정 가능함’을 목표로 한다.

| 위험 | 어떻게 나타나는가 | 방어와 실패 시 조치 |
| --- | --- | --- |
| 박자와 onset 혼동 | ‘뚠’ 전에 다른 음에 여러 번 반응 | 서로 다른 트랙으로 표시하고 평가도 분리 |
| 절반·두 배 템포 | 박자마다 두 번 켜지거나 절반만 반응 | 곡별 박자 대조, 대안 후보와 수동 교정 제공 |
| 셔플·당김음·변속 | 모든 큐를 균등한 간격으로 만들면 어긋남 | 실제 시각 배열 사용, 강제 스냅 금지 |
| 잔향·지속음·보컬 | 한 소리가 여러 타격으로 검출 | 후보의 중복 평가, 원인별 비교. 불확실 큐는 자동 강조 금지 |
| 압축된 강한 음원 | RMS가 계속 높아 모두 클라이맥스 취급 | 상대값·밀도·반복 변화 보조, 구간 효과 수동 확정 |
| 무음의 잡음 증폭 | 작은 잡음이 곡 상대 정규화로 강한 후보가 됨 | 절대 무음 기준과 상대 기준 병용, 원단위 보존 |
| 단일 곡 과적합 | 예시 곡만 좋고 다른 곡은 실패 | 미사용 검증곡 분리, 곡별 수치를 따로 공개 |
| 과도한 연출 밀도 | 정확한 onset이어도 너무 바쁘게 보임 | 모든 onset 평가와 선택한 조명 악센트 평가를 분리 |
| 불확실한 구간 판정 | 후렴인데 한 쌍, 조용한데 전체 플래시 | 미확정 표시, 구간 수정. 위험 효과 자동 생성 안 함 |

### 실패 원인 확인 순서

먼저 분석 클릭이 실제 소리와 맞는지 본다. 맞으면 최종 큐 클릭이 의도한 악센트인지 본다. 그것도 맞으면 모의 프레임의 시작과 감쇠를 본다. 마지막으로 실제 전구의 시간차와 흔들림을 측정한다. 앞 단계가 틀렸는데 다음 단계의 보정값을 바꾸지 않는다.

### 오픈소스를 쓰더라도 남는 문제

분석 라이브러리는 ‘이 노래를 어떻게 연출하면 아름다운가’를 결정하지 않는다. 또한 드럼 없는 음악에 반복 박자가 반드시 존재하는 것도 아니다. 같은 음원에 여러 음악적 해석이 가능한 경우에는 자동 실패를 숨기지 않고 유지형 효과 또는 수동 악센트 편집으로 대응한다.

기본 원칙은 낮은 신뢰도에서 효과를 더 만들지 않는 것이다. 그렇다고 모든 저신뢰 구간을 암전시키지는 않는다. 마지막으로 확인한 유지 상태 또는 사용자가 지정한 소등을 따른다.

### 초기 현장 제약

첫 버전은 현재 프로젝트의 단일 Bridge와 A/B 동일 크기, 총 10개 이하라는 제한을 유지한다. 슬롯 수는 배열에서 읽고 5쌍을 코드에 고정하지 않는다. 새 Bridge 제품의 기능이나 여러 Bridge 동시 출력으로 범위를 넓히는 일은 별도 검토다.

사용자가 배치한 전구 이름이 바뀌어도 이름 문자열만으로 매핑하지 않는다. 장비 ID와 논리 슬롯 매핑을 확인한다. 빠진 전구가 있으면 조용히 다른 전구로 대체하지 않고 시작 전 경고한다. 연결 복구 후에는 자동으로 공연을 재개하지 않는다.

### 안전과 운영

첫 시연은 웹 미리보기, 실제 출력은 낮은 밝기부터 확인한다. 스트로브는 첫 버전에서 제외하고 급격한 전체 점멸이 포함되면 경고한다. 밝기 상한은 두되 특정 주파수나 밝기가 모든 관객에게 안전하다고 보장하지 않는다. 공연장 운영 기준에 따른 검토가 별도로 필요하다.

음원은 로컬에서 처리하고 외부 분석 서비스에 자동 업로드하지 않는다. 경로 조작과 과대 파일 입력을 막고, 작업 취소 시 완성되지 않은 파일을 ‘분석 완료’로 표시하지 않는다. 모델을 포함한 배포물은 버전과 체크섬을 검증한다.

## 12 어떤 시험을 통과해야 다음으로 가는가

**아래 숫자는 달성한 성능이 아니라 착수 전에 합의할 초기 목표다.** 목표를 못 맞추면 수치를 숨기거나 자동으로 낮추지 않고 분석 방식 또는 지원 범위를 재논의한다.

### 음악 평가 세트

최소 8곡을 준비한다. 규칙적인 전자음악, 잔잔한 피아노·발라드, 보컬과 잔향이 많은 곡, 라이브 드럼·템포 변화, 드럼 없는 지속음 곡, 셔플·당김음 등 서로 다른 성격을 포함한다. 적법하게 사용할 수 있는 사용자 제공 음원으로 진행한다. 지금 실제 확인 자료는 예시 한 곡이므로 다곡 성능은 미검증이다.

곡당 도입·강한 구간·전환 등 20~30초 구간 세 곳을 검토한다. 최소 3곡은 튜닝에 쓰지 않는 검증곡으로 남긴다. 분석기의 onset 정답, 음악의 Beat 정답, 연출에서 강조할 악센트 목록을 구분해 기록한다. 모호한 순간은 정답을 강요하지 않고 평가에서 별도 집계한다.

| 검증 단계 | 초기 통과 목표 또는 규칙 |
| --- | --- |
| 타격 후보 | 검토한 onset 기준 ±50ms 내 매칭. 곡별 Precision·Recall 보고. 초기 목표 각각 90%·85% |
| 박자 추적 | 합의한 Beat 기준 ±70ms 창과 곡별 F1 보고. 초기 목표 F1 0.85. 절반·두 배 오류 별도 기록 |
| 연출 초안 | 30초 구간당 불필요한 큐·누락·위치 이동 수정 횟수 기록. 초기 목표 주요 수정 3회 이하 |
| 반복 타격 | 한 악센트에 여러 펀치 발생 사례를 따로 집계. 단순 총 타격 수 감소로 합격 판정 금지 |
| 결정적 재생 | 동일 음원·악보·배치·시드에서 동일 시각의 프레임 동일. 전체·중간 재생 결과 일치 |
| 저장·복구 | 재분석, 재생성, 앱 재시작, 충돌 후 수동 편집 및 삭제 정보 보존 |
| 실제 출력 | 보정 후 오디오 대비 절대 오차 p95 100ms 이하를 초기 목표로 측정. 평균과 최대·누락도 함께 보고 |

Precision은 검출한 것 중 맞은 비율, Recall은 정답 중 찾아낸 비율, F1은 둘의 균형 점수다. p95 100ms는 측정한 오차의 95%가 100ms 이내라는 뜻이며 최악값 보장이 아니다.

±50ms onset 평가는 mir_eval의 기본 평가 창을 참고했다. 이는 사람의 만족도나 장비 지연 허용치와 다르다. [S11] 정상 onset이어도 연출에는 불필요할 수 있으므로 점수를 하나로 합치지 않는다.

### 개발자가 먼저 하는 시험

무음, 단일 타격과 잔향, 빠른 연타, 지속음 떨림, 변속, 스테레오 역위상, 44.1/48kHz, 긴 파일, 탐색·반복 재생, 두 탭 충돌, 통신 끊김을 자동 시험한다. 분석 시간과 최대 메모리는 목표 PC에서 5분 곡으로 측정하고 실측 전 처리 속도를 약속하지 않는다.

실제 지연은 동일 녹음·촬영에서 소리와 빛을 함께 확인한다. 카메라 프레임 간격과 오디오·영상 자체 오프셋도 기록한다. 사람이 버튼을 누른 반응시간만으로 정확도를 판정하지 않는다. 사용자 평가는 개발자 검증 뒤 승인할 단계에만 요청한다.

## 13 구현 순서와 승인 기준

이 계획은 검토 대기 상태다. 아래 구현 단계는 모두 미착수다. 단계별 산출물과 실패 시 행동을 기록하고, 한 번에 분석·연출·출력 세 층을 모두 바꾸지 않는다.

| 단계 | 구현 및 산출물 | 다음 단계로 가는 조건 |
| --- | --- | --- |
| 0 보존과 계약 | 기존 파일 백업, 읽기 전용 레거시 경로, 새 schema와 평가곡 목록 | 기존 데이터 무변경 확인, 평가 기준 승인 |
| 1 분석기 비교 | 분리 환경의 후보 분석, 고정 버전, 곡별 클릭·수치 보고 | 시간 원점 확인, 라이선스·설치 통과, 후보 선택 |
| 2 분석 검토기 | 파형과 Beat·onset 표시, 클릭 선택, 누락·중복 주석 | 여러 곡에서 원인 구분 가능. 조명 아직 연결 안 함 |
| 3 한 쌍 악보 | 선택 사건→단일 쌍 펄스, 큐 추가·삭제·이동, revision 저장 | 중복 점등·잔류 없음, 수동 편집 보존 |
| 4 구간 연출 | 유지·전체 펀치·소등, 구간 편집, 팔레트, 충돌 규칙 | 초안 수정량·사용자 음악적 평가 통과 |
| 5 출력 재생기 | 서버 시계, 세션·버퍼, 탐색·정지, Hue 어댑터 연결 | 모의 프레임 일치와 물리 지연·장애 시험 통과 |
| 6 이전과 배포 | 기존 곡 복사 이관, 내보내기, 설치 안내, 현장 체크리스트 | 새 PC·무인터넷 재생 및 복구 시험 통과 |

### 실패하면 어떻게 할 것인가

1단계에서 분석기가 기존보다 낫지 않으면 새로운 자동 효과를 추가하지 않는다. 후보 교체나 수동 큐 중심 범위로 축소하는 안을 제시한다. 3단계에서 ‘한 타격 한 쌍’이 맞지 않으면 전체 펀치나 화려한 패턴으로 넘어가지 않는다. 5단계의 지연 문제가 남으면 현장용 완성본이라고 부르지 않는다.

초기 구현은 별도 기능 경로로 두고 기존 재생 기능을 즉시 삭제하지 않는다. 새 형식의 악보를 기존 자동 업그레이드 함수에 넣지 않는다. 첫 사용자가 승인한 공연본과 데이터 복구 시험을 통과한 뒤 기본 화면을 전환한다.

### 리뷰에서 정리한 결론

사전 분석·자동 초안·수동 보정·확정 재생을 추천한다. 핵심 위험은 onset과 원하는 악센트의 차이, 수동 편집 덮어쓰기, 검출 오류와 출력 지연의 혼동이다. 분석기 버전·선택 임계값·다곡 수정량·목표 PC 성능·현장 지연은 아직 미확정이다.

### 이 문서 승인 시 시작할 일

먼저 0단계와 1단계만 진행한다. 기존 데이터 보존 확인과 분석기 비교 보고서를 만든 뒤 결과를 검토한다. 승인 전에는 새 분석 패키지 설치, 기존 데이터 변환, 재생 방식 교체를 진행하지 않는다. 일정은 목표 PC에서 비교 시험 소요를 측정한 후 산정한다.
